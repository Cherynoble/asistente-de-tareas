## 1. Multi-provider AI

### Why
Every AI call went straight to the Anthropic SDK from five different places.
That made "use a Chinese model" impossible without touching all five, and it
meant there was no single place to put retries, JSON parsing, or a provider
switch.

### What `src/ai/` is
The only code in the app that talks to an AI vendor. Feature code now asks for
`aiProvider()` (chat/tools/vision) or `aiJson()` (structured extraction) and
never imports a vendor SDK.

| File | Lines | Responsibility |
|---|---:|---|
| `types.ts` | 138 | Neutral message/tool/vision types, `withRetry`, `extractJson` |
| `anthropic.ts` | 133 | Anthropic adapter over the official SDK |
| `openai.ts` | 176 | Generic OpenAI-compatible adapter (plain `fetch`, no SDK) |
| `providers.ts` | 99 | Named presets + their defaults |
| `pdf.ts` | 79 | Local PDF → text extraction for non-Anthropic providers |
| `index.ts` | 164 | Config resolution, settings persistence, entry points |

### Providers
Presets ship for **Anthropic**, **Kimi (Moonshot)**, **DeepSeek**, **Qwen**,
**GLM (Zhipu)**, **Ollama** (local, no key), and **custom**. Every field stays
editable — model names on these platforms change every few months, so nothing in
`providers.ts` is load-bearing beyond first setup.

The non-Anthropic adapter is a single generic OpenAI-compatible client rather
than one integration per vendor, because every major Chinese lab exposes that
dialect. Adding a new provider is a row in `PROVIDER_PRESETS`, not new code.

It uses plain `fetch` **on purpose**: the packaged app's `node_modules` are
frozen inside the shell, and online updates ship only `dist/` + `public/`. A
dependency-free adapter can therefore ship as a normal online update.

### The five call sites that moved
- `extract/claude.ts` → **`extract/extractor.ts`** (`ClaudeExtractor` →
  `ModelExtractor`); prompt and output contract unchanged.
- `extract/vision.ts` — image/PDF description.
- `chat/index.ts` — the agent's whole tool loop, now provider-neutral.
- `clients/classify.ts` — also dropped its fragile `indexOf('[')` JSON parsing
  in favour of the shared `extractJson`.
- `extract/translate-tasks.ts`.

### Route gating
`getApiKey()` checks became `hasAiKey()`, so a keyless local provider (Ollama)
counts as configured once it has a base URL and model. `getApiKey()` still
exists for the Anthropic-specific key; `anthropicClient()` was deleted.

### Settings keys
Per-provider, so switching back and forth never loses a key:

```
ai_provider            preset id ('anthropic' default)
ai_model:<provider>    model override
ai_base_url:<provider> base URL override
ai_key:<provider>      API key  (anthropic reuses the legacy anthropic_api_key)
ai_vision:<provider>   '1'/'0' — does the chosen model accept images
```

### UI
Ajustes → **Proveedor de IA**: provider dropdown, model, base URL (hidden for
Anthropic), a vision checkbox, per-provider key field, and **Probar conexión**.

- `GET /api/ai` — presets + stored config + which provider is active (never keys)
- `POST /api/ai` — save; re-arms the nightly cron since `hasAiKey()` may change
- `POST /api/ai/test` — one real round trip, so a typo'd key/model/URL surfaces
  in Ajustes instead of in a silently failing 3am cron run

### Vision and PDFs
Images work anywhere the configured model supports them; when it doesn't, the
adapter substitutes an explanatory note rather than firing a doomed request.

PDFs are the one genuine capability gap. Anthropic reads them natively. For
everyone else `ai/pdf.ts` extracts the text locally with **pdfjs-dist** (pure
JS, no native module, so it can't break the Electron ABI setup) and inlines it.
Verified against a real WhatsApp PDF from the live data directory (3 pages,
clean extraction). Scanned image-only PDFs return an explanatory note instead of
a guess, and a missing package degrades to a message rather than a crash.

## 2. Codebase-health pass

### Server split
`src/server/index.ts` went from **1,621 → 152 lines**. It is now middleware,
router mounts, and `listen` — and remains the Electron shell's import target, so
the bundle path is unchanged.

```
src/server/
  index.ts        152   middleware + mounts + listen
  helpers.ts      235   clampNum, SSE writer, includedChats, attachmentEntries
  lifecycle.ts    123   daily cron, nudge loop, reminder sweep, wake detector
  routes/tasks.ts      197   Bandeja · Tareas · Archivo · Papelera · bulk
  routes/messages.ts   ~350  Mensajes tab, attachments, backfill, SSE stream
  routes/chat.ts       ~190  threads, turns, uploads, memory, agenda, digest
  routes/clients.ts    ~180  Clientes roster, upserts, auto-classify
  routes/settings.ts   177   Ajustes, AI provider, stats, diagnostics, reminders
  routes/whatsapp.ts   102   multi-account management
```

### Frontend split
`public/app.js` (2,845 lines at the last release, 2,902 by the time of the
split) became **11 ordered classic scripts** sharing one global scope,
totalling 2,958 lines including per-file headers:

```
app-core.js → app-tasks.js → app-pipeline.js → app-clients.js →
app-attachments.js → app-messages.js → app-trash.js → app-chat.js →
app-settings.js → app-whatsapp.js → app-init.js
```

**The order in `index.html` matters** — it mirrors the original file, and
`app-init.js` (the startup IIFE) must stay last. Keep new top-level names unique
across the files. Deliberately *not* ES modules: that would have required
rewriting every cross-file reference, a much riskier change for zero benefit
here.

### `nameMap()` caching
It scanned and grouped the entire messages table, yet ran on nearly every
request and inside `resolveClientHint()` on every task insert. Now cached for
30 s, with `invalidateNameCache()` called by the client write routes so renames
still appear immediately.

> **Contract:** any code that writes to `clients` *without* going through the
> API routes must call `invalidateNameCache()` itself. The smoke test does, and
> documents why.

### Per-client task dedup
`saveTasks()` rule 1 keyed on the normalized title alone, so two *different*
clients asking for the same thing collapsed into one task and the second
client's request was silently dropped. Rule 1 now matches on title **and**
client. An empty hint on either side still matches conservatively, so hint-less
proposals can't stack duplicates. The chat agent's `create_task` got the same
treatment, so both task-creating paths agree.

### One definition of the attachment lists
`src/attachments.ts` owns the `'||'`-joined columns. `joinAtt()` neutralizes
separators embedded in a component at write time — previously a filename
containing `||` would have shifted every list after it and paired index *i* with
the wrong file. `attachmentEntries()` replaces three hand-synced copies of the
gallery decoration logic that had to agree field-for-field.

### Failures that used to be invisible
- **WhatsApp `persist()`** had a bare `catch { return 0 }`. A systematic insert
  failure would have dropped every incoming message with no evidence anywhere.
  It now logs the first failure of a burst and every 50th after.
- **The nightly cron** failing meant tasks quietly stopped appearing, with the
  only trace in a log the owner never reads. It now fires a native
  "El análisis nocturno falló" banner naming the cause.

### FTS5 search
Message search was a `LIKE '%term%'` scan of every body. There is now a
`messages_fts` virtual table using the **trigram** tokenizer, kept in sync by
triggers, behind `bodyFilterSql()` — used by the Mensajes search and filter and
by the chat agent's `search_messages`.

Trigram specifically, because it preserves the substring semantics the search
always had *and* works on Chinese text, which has no word boundaries for the
default tokenizer. Terms under 3 characters, and installs whose SQLite lacks
fts5, fall back to LIKE automatically.

Verified on the live DB: case-insensitive substrings, `卫生纸`, and a literal
`20%` all match correctly.

## 3. Two real bugs the new tests caught

**Pager duplication (pre-existing, shipped).** Opening a chat anchored on a
search hit (`dir=around`) duplicated messages sharing the anchor's timestamp:
the "after" half filtered on `ts >=` only, ignoring the message id, so rows the
"before" half had already returned came back again. Bulk imports routinely share
timestamps, so this was reachable in normal use. `runFrom()` now takes the
composite `(ts, id)` cursor like every other direction.

**FTS index never actually built (introduced and caught in the same session).**
The first version decided whether to build the index by comparing row counts —
but on an external-content fts5 table, `COUNT(*)` is answered from the *content*
table, so it matched even when the index was empty, and search silently returned
nothing on the existing database. Now gated by an explicit one-time `fts_built`
marker in `settings`. Confirmed on the real DB: `[db] built messages_fts (3790
rows)`.

## Before releasing

1. **`pdfjs-dist` is a new dependency.** Online updates ship only `dist/` and
   `public/`, never `node_modules` — so the first release that relies on it
   needs a freshly built `.app` delivered to your dad, plus a
   `MIN_SHELL_VERSION` bump. (The code degrades gracefully if the package is
   absent, so a code-only release won't crash; PDFs on non-Anthropic providers
   just won't be readable.)
2. **Bump the version** in `package.json` (1.7.2 → 1.8.0) before
   `npm run release`.
3. **The dev `.env` `ANTHROPIC_API_KEY` is invalid** — it returns 401 straight
   from the API, confirmed by direct curl, so it was revoked or rotated at some
   point. Replace it, or paste a working key in Ajustes.
4. **Anthropic remains the default provider.** Nothing about your dad's install
   changes until you decide it should; validate extraction quality on real
   messages first.
